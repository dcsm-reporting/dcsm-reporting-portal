The decision

The old system — nine interlinked Google Sheets, five Apps Script projects, a Form, two Slides decks — failed. The recurring breakages traced to two things: a free-text teaching-area name used as a primary key in five places, and two data channels merged by hand. The rebuild removes both.

The first proposal built the replacement as a Google Apps Script Web App. That clears the $0 bar but the developer experience taxes every future maintainer, and the UI can't be made fluid. This version is a modern web app on Cloudflare.

RequirementHow this meets it
$0 forever, no cardPages + Workers + D1 + KV are free with no card, all first-party — the free tier is a published product, not startup runway. (On Vercel the hosting is free but every database option is a separate third-party free tier — the exact failure mode the mission wants gone.)
No credentials to storeD1 binds straight to the Worker — no connection string. Auth is Cloudflare Access — no OAuth secret in the app. Deploys use wrangler login or the Git integration.

Reuse the tested logicD1 is SQLite, so the Python reference's schema and queries port almost directly instead of being reinvented.

  • IMOS KI report JSON — pasted weekly
  • Area To Ward Key CSV — bundled, one-time seed
  • STL friend / on-date entry — in the app
  • DCSM Contacts — one read, on demand
→

Worker (Hono) + D1

  • validate · normalise · crosswalk · roll up
  • D1 (SQLite): facts, ward facts, crosswalk, friends, config, audit
  • runs behind Cloudflare Access
→

Outputs

  • This Week · Month · Stakes · Trends · Chase list
  • Board PNGs → group chats
  • Stake report → drafted, a person sends from Gmail

One deploy: the Worker serves /api/* and falls back to the built SPA for everything else. src/pipeline/ is pure and has no platform dependency — it runs identically in the test runner and in the Worker.

Platform mechanics

  • Worker: Hono router. POST /api/import validates, offers a dry-run, then commits. Read endpoints assemble the boards from stored facts.
  • D1: bound as DB; bulk inserts are chunked to D1's 100-parameter limit. Recovery has three layers: Cloudflare's built-in 30-day time-travel, an on-demand wrangler d1 export SQL dump (scripts/backup.sh), and a dormant weekly GitHub Action that commits that dump to the repo.
  • Auth: Cloudflare Access sits in front in production. The Worker reads the injected email header for attribution; DEV_USER stands in locally.
  • Directory: DCSM Contacts shared read-only to the role account, synced to directory_person on demand, cached. The only spreadsheet the app ever touches.

Identity & crosswalk

The module that makes the system survive transfers. The old system had no stable identifier for a teaching area; this one owns one.

  • canonical_area_key — a slug the mission owns (fairfax, alexandria-1a), created once, never changed as IMOS area IDs churn.
  • area_crosswalk — effective-dated imos_area_id → canonical key. At a transfer, add rows; history stays continuous under the canonical key.
  • area_ward — effective-dated canonical key → (ward_unit_id, ward_name, stake), anchored on the IMOS org.id (a real unit number, far more stable than area IDs).

Seeding: POST /api/seed {weekStart} reads that week's stored raw payload plus the bundled CSV. On the real 2026-08-24 data it resolves 100% of areas to a stake — 107 areas, 112 ward rows, 11 stakes, nothing unmapped. Run it once per structure (post-transfer, and again for a pre-transfer week with an earlier validFrom). Any unmapped IMOS id thereafter surfaces on the Import page and in Admin with a one-field "attach to canonical key" control.

What's left

Until then, run scripts/backup.sh by hand before any migration or bulk load. Cloudflare's own 30-day time-travel covers the rest.
  • Directory sync — optional now the EMAILS sheet covers stake reports; would add leader name/phone to the Chase list.
  • Historical KI backfill — abandoned. The legacy workbook's RemoveDuplicates / Form Responses sheets are keyed by form-submission timestamp, not report week, and only a rolling transfer window is ever fully populated — there is no clean pre-IMOS weekly series to load. Trends and Month begin with the IMOS-paste era (2026-06).

Cutover reconciliation

Unchanged from the earlier analysis — settle these during a parallel week. None are blockers; each is a place the old system may have been wrong.

  1. MLC-area share runs high. The rule flags ~40 areas as MLC (any AP/ZL/STL/STLT) vs. the old hand-list of ~27. On 2026-08-24 the portal shows NP share 30%. Narrow MLC_POSITIONS in src/pipeline/constants.ts or add a config override once the old LeadershipAreas list is in hand. Config-only.
  2. Monthly totals differ ~1–4% from the old "Mission at a Glance" (window offset — four most recent stored weeks vs. a rolling four-week window). The NMS/RCA gap is larger and needs a side-by-side.
  3. Weekly mission totals run ~1–2% above the old numbers — expected: the old figures were Monday-night preliminary; a same-day IMOS pull is more complete.
  4. Percent rounding — the pipeline uses round-half-to-even (matches the Python); the old Apps Script decks used round-half-up. A ≤1-point cosmetic difference only on exact halves.

Operating it

The one-time setup (role account, Cloudflare, Access, first deploy) is done. Day to day:

  • Weekly — the Import page shows the exact IMOS URL for the week and an "Open in IMOS" button. Sign in to a missionary account, copy the JSON, paste, commit. The Weekly console tracks the rest.
  • Baptisms — STLs keep editing the Baptisms (MLC) sheet exactly as before. A bound Apps Script pushes it to the portal every 15 minutes; the Friends page and stake reports follow.
  • Transfers — Structure → Rollover: pick the first week of the new transfer, review the proposed area/ward mappings, apply. The bridge auto-discovers any new zone tabs.
  • Ship an update — npm run deploy from the repo.
